# 🔴 数据丢失事故报告与恢复指引（2026-10-28）

> **结论先行：你的日记数据没有丢失，全部还在手机上。**
> 这次是 B0-2（分键存储）引入的**读取 bug**，不是数据被删除。
> 修复后重新打开 App 即自动恢复，无需任何手动操作。

---

## 一、事故现象

升级后再次打开 App，日记列表显示 **0 篇**（时间线、日历、统计全部为空）。

---

## 二、根因（我的代码缺陷）

我在 `_loadDiariesFromSplitKeys()` 里写了这一行：

```dart
final List<int> ids;
if (indexJson == null || indexJson.isEmpty) {
  ids = const [];
} else {
  ids = jsonDecode(indexJson)          // ← 返回 List<dynamic>
      .cast<num>()
      .map((e) => e.toInt())
      .toList(growable: false);         // ← 运行时类型是 List<dynamic>
}
```

`jsonDecode(...).cast<num>().map(...).toList()` 产出的**运行时类型是 `List<dynamic>`**，赋给声明为 `List<int>` 的变量会直接抛：

```
type 'List<dynamic>' is not a subtype of type 'List<int>'
```

更糟的是：这行位于 `_loadData()` 的 `try/catch` 里，异常被**吞掉**了，只打印一句「加载数据失败」，然后 `_diaries` 保持为**空列表**。

于是 App 认为「一篇日记都没有」，把 0 篇展示给你 —— 而磁盘上：
- `diary_<id>` 分键（迁移时写入的）**全部都在**
- `diaries_data` 旧键（我迁移时**故意没删**的）**也在**

**数据完好，只是读不出来。**

### 为什么「再次打开」才出现

首次启动时迁移刚跑完，`_diaries` 是内存里现成的列表，所以正常。重启后走「从磁盘加载」路径，才踩到这行类型错误。

### 我的两个设计失误

1. **类型错误没有在编译期被发现** —— 因为 `jsonDecode` 返回 `dynamic`，`dynamic` 赋值给 `List<int>` 是运行时检查。单测也没覆盖这条路径（我写的迁移测试只测了「迁移后首次读」，没测「重启后读」）。
2. **异常被静默吞掉** —— `_loadData` 的 `try/catch` 把致命错误降级成了一行日志，导致「数据全丢」这个最严重的状态没有任何提示。

## 三、已做的修复

### 修复 1：类型错误 + 索引损坏容错

```dart
try {
  ids = List<int>.from(
    (jsonDecode(indexJson) as List).map((e) => (e as num).toInt()),
  );
} catch (e) {
  // 索引格式损坏 → 当作没有索引，交给自愈逻辑重建
  print('日记索引解析失败，将重建: $e');
  await _loadDiariesByScanningKeys();
  return;
}
```

### 修复 2：三层自愈（**核心保障**）

新的加载逻辑原则：**磁盘上的真实数据永远高于索引缓存**。索引只是加速用的缓存，坏了必须能重建，绝不把「读到 0 篇」当作真相。

```
启动加载
  ├─ 有迁移标记 → 从索引读
  │    └─ 读到 0 篇？ → 自愈①扫描所有 diary_<id> 键重建索引 → 重读
  │         └─ 仍为 0？ → 自愈②回退旧键 diaries_data 重新迁移
  └─ 无迁移标记 → 看旧键
       ├─ 有 → 迁移
       └─ 无 → 先扫描分键（可能是「迁移了但标记丢了」）→ 有数据则补写索引+标记
```

### 修复 3：迁移顺序加固

迁移改为「写分键 → 写索引 → **校验索引条数** → 置标记」。任一步失败都不置标记，下次启动重试；分键写入本身幂等，重复执行不丢数据。

### 修复 4：显式救援入口

新增 `DatabaseService.recoverFromDisk()`：强制以磁盘为准重建全部日记，返回恢复数量。可用于设置页的「修复数据」按钮。

## 四、你现在该怎么做

### 首选：直接用修复后的版本重新打开 App

**不需要任何手动操作。** 启动时会自动：

```

```
或通过「我的 → 数据管理 → 备份管理」查看。

数据管理 → 云同步 → 下载。

**方案 C：让我加一个「从旧键强制恢复」的界面按钮**
`diaries_data` 旧键我从未删除，只要它还在，就一定能恢复。

## 六、我的责任与改进

这次事故的直接责任在我：我改动了**用户数据存储格式**，却没有做到以下三点：

1. **没有为「重启后读取」写测试** —— 只测了迁移当晚的内存状态，这是最典型的「测了 happy path，漏了持久化路径」。用户数据的持久化路径必须双向验证（写入后从磁盘重新读一次）。
2. **没有把致命错误升级为可见错误** —— 数据加载失败应该是**阻塞性错误页**（「数据读取异常，请勿操作，正在尝试恢复」），而不是一行 `print` 后静默显示空列表。
3. **一次性引入了过多变更** —— B0-2 涉及存储格式迁移，本应**单独提交、单独灰度、单独验证**，我却把它和另外 9 项改动一起上线，放大了风险面。

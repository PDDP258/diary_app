# 大学生课表导入功能 · 实现路径探索

> 调研日期：2026-09-07 | 目标项目：小记日记（Flutter 3.x + Provider + SQLite）
> 三条路径：**① 规格文档导入**、**② 教务系统导入**、**③ 图片识别导入**

---

## 〇、总体结论（先看这里）

| 路径 | 开发成本 | 覆盖率 | 维护成本 | 用户体验 | 建议优先级 |
|------|---------|--------|---------|---------|-----------|
| ① 规格文档（Excel/CSV/JSON 模板） | ★ 低（1-2 周） | 100%（兜底） | 几乎为零 | 中（需用户动手填/转） | **P0，先做兜底** |
| ② 教务系统导入 | ★★★ 高，且持续 | 取决于适配数（头部学校） | 极高（教务系统会改版） | 极高（10 秒导入） | P1，借力社区 |
| ③ 图片识别（OCR） | ★★ 中（用云 API）/ ★★★★ 高（自研） | 理论上所有学校 | 低-中 | 高（拍照/截图即用） | **P1，性价比最高** |

**推荐落地顺序**：① 兜底先行 → ③ 云 OCR 快速上线 → ② 用「WebView + JS 适配」架构逐校扩展。

国内行业标杆参考：
- **WakeUp课程表**（开源，Kotlin）：适配 1800-3000+ 所高校，核心是「学校适配器」架构。
- **小爱课程表**（小米）：开放适配平台，社区贡献 `Provider / Parser / Timer` 三段式 JS 适配代码，是本调研最重要的架构参考。
- **超级课程表**：早年以爬虫农场 + 图片识别起家。

## 一、规格文档导入（标准模板文件）

### 定位
不依赖任何学校系统的**兜底通道**，也是另外两条路径的最终数据落点格式——无论爬虫还是 OCR，最终都应归一化成同一套「课表规格文档」。

### 实现思路

1. **定义 App 内部标准课表模型**（核心，先做）：
   ```
   Course {
     name, teacher, location, weeks[], dayOfWeek(1-7),
     startSection, sectionCount, color?, note?
   }
   SemesterConfig {
     startDate, totalWeeks, sections[{index, startTime, endTime}]
   }
   ```
   关键是「周次表达」的解析器：国内教务输出形如 `1-16周`、`2,4,6-8周(单/双)`，需要一个健壮的 `weekStr2IntList()`（小爱适配社区已有成熟实现，处理全角逗号、区间、单双周）。

2. **对外提供三种模板**：
   - **Excel 模板**（最实用）：一行一门课的一次上课安排。Flutter 端用 `excel` package 解析；用户在电脑或手机上用 WPS 填。App 内提供「下载模板」→「导入」闭环。
   - **CSV/TSV**：给会折腾的用户，实现几乎免费。
   - **ICS（iCalendar）**：部分学校（尤其新教务/智慧校园）已支持直接导出 `.ics`。解析 `VEVENT` + `RRULE:FREQ=WEEKLY` 即可，`icalendar_parser` 或直接手写（ICS 语法简单）。这是"规格文档"里最高级的形态，建议支持。

3. **交互闭环**：导入后进入「预览确认页」→ 可视化课表网格，允许逐格点修正 → 入库。

### 成本与风险
- 纯 Dart 实现，无网络依赖，无合规风险。
- 唯一难点是周次/节次字符串解析的健壮性，建议配单元测试覆盖常见模式。

## 二、教务系统导入（爬虫/适配器）

### 2.1 国内教务系统版图

| 厂商 | 市场占有率（体感） | 技术特征 |
|------|------|------|
| **正方**（新/旧两版） | 最高 | 旧版：ASP.NET WebForms + `__VIEWSTATE` + iframe；新版：`jwglxt` 前缀，登录后可直接 POST `kbcx/xskbcx_cxXsgrkb.html` 拿 **JSON**（最友好） |
| **强智** | 次高 | 有 `app.do?method=authUser` 移动端接口，登录返回 token，之后 `getKbcxAzc` 直接返回课表 JSON |
| **青果** | 中等 | 登录密码 MD5 变形加密（前端 js 里可逆向），课表在 `wsxk/stu_zxjg_rpt.aspx` 等页面，需解析 HTML |
| URP / 树维 / 新中新 / 弘成 / 各厂自研 | 长尾 | 千奇百怪 |

### 2.2 关键架构决策：WebView + JS 注入（强烈推荐）

这是**小爱课程表/WakeUp 验证过的最佳实践**，比「App 内原生模拟登录」好得多：

**流程：**
1. App 内嵌 WebView 打开学校教务系统登录页；
2. **用户自己手动登录**（验证码、滑块、统一身份认证、企业微信扫码全部交给用户和浏览器内核解决——这是绕过验证码军备竞赛的关键）；
3. 登录态（Cookie/Session）天然在 WebView 里，App 注入 **Provider JS**：要么直接 `document` 取课表页 HTML，要么带登录态 `fetch()` 后端接口拿 JSON；
4. **Parser** 把原始数据归一化成标准课程 JSON（可用 JS 在 WebView 里跑，或回传 Dart 用 `html` package 解析）；
5. **Timer** 返回节次时间配置。

**为什么是三段式**：获取（Provider）/ 解析（Parser）/ 时间配置（Timer）解耦后，同一教务厂商的不同学校往往只需改 URL 和课表 DOM 选择器，适配边际成本极低。小爱平台上一个熟手适配一所学校约 2 小时。

**Flutter 落地方案**：
- `webview_flutter`（或 `flutter_inappwebview`，JS 桥更强）+ `JavascriptChannel` 回传结果；
- 每所学校一份适配描述：`{schoolId, name, loginUrl, providerJs, parserJs, timerJs}`；
- **适配包云端下发**（放对象存储/GitHub Raw，App 启动时拉取清单），学校改版不用发版——这是必修课，教务系统一年一小改。

### 2.3 不建议的方案
- ❌ App 内原生 HTTP 模拟登录：验证码（图形/滑块/极验）、密码前端加密（每校一套 MD5 变形）、ViewState 都会让你陷入无尽的逆向泥潭，且名校普遍上了统一身份认证（CAS/OAuth），基本走不通。
- ❌ 自建服务端爬虫农场代登录：帮用户存学号密码 = 巨大的隐私合规风险（《个人信息保护法》），且校园网常限制校外访问，还要维护打码平台。WakeUp 早年这么做，后来也转向了本地 WebView 方案。

### 2.4 冷启动策略
- 优先适配头部 N 所高校（按用户量投票/申请制）；
- 把适配接口文档化，开放「用户投稿适配」通道（抄小爱的作业）；
- 教务厂商级复用：新版正方的 JSON 接口基本通吃所有用新版正方的学校，一套适配打一片。

## 三、图片识别导入（OCR）

### 3.1 技术路线对比

| 方案 | 准确率 | 成本 | 备注 |
|------|--------|------|------|
| **云 OCR 表格识别 API**（百度/腾讯/阿里「表格文字识别」接口） | 高 | 按次计费（约 0.01-0.05 元/次，教育类常有免费额度） | **推荐起步方案**，0 模型工作 |
| 自部署 PaddleOCR PP-Structure（SLANet 表格结构识别 + PP-OCR 单元格识别） | 高 | 一台服务器 + 维护 | 规模化后降本之选 |
| 端侧 OCR（ML Kit / Paddle Lite）+ 自写版面逻辑 | 中 | 免费 | 课表是无线框/彩色块排版，端侧纯文字识别拿不到结构，需自己写单元格切分（OpenCV 找线/连通域），效果不稳 |
| 多模态大模型（拍照→让模型直接输出结构化 JSON） | 对规整课表很高，且天然理解「周一第1-2节」语义 | 按 token 计费，单次约几分钱 | 2026 年这已是相当现实的方案，可做为云表格 OCR 失败时的降级通道 |

### 3.2 推荐管线（云 API 版）

```
用户拍照/上传截图
  → 图像预处理（矫正、裁剪，可选）
  → 表格结构识别（行列/合并单元格 → 网格）
  → 单元格文字识别
  → 语义解析：单元格文本 → Course 列表
      （难点：一格多门课、"1-16周 单周"、地点教师混排换行）
  → 课表预览确认页（必须！OCR 不可能 100% 对，逐格点编辑修正）
  → 入库
```

两条工程要点：
1. **合并单元格还原**：课表的 rowspan（一门课占 2-3 节）必须正确展开为节次区间；
2. **确认页是产品必需品而非可选**：识别错了让用户改一格，比重做一次识别体验好得多。

### 3.3 与路径②的关系
OCR 是教务适配的**天然补充**：没适配的学校、教务系统打不开的假期、截图转发来的课表，都靠它兜住。两者共用同一个「预览确认页」和标准课程模型。

## 四、对小记日记项目的落地建议

1. **数据层**：现有 SQLite 双端架构（原生 + Web SharedPreferences）加 `courses` / `semester_config` 两表；与日程模块打通——课程可一键转为重复日程事件，蹭上已有的提醒/徽章体系。
2. **第一步（1-2 周）**：标准课程模型 + 周次解析器 + Excel/CSV/ICS 导入 + 课表预览页。立刻可用、零风险。
3. **第二步（2-3 周）**：接入一家云表格 OCR（百度/腾讯教育接口），拍照导入上线。
4. **第三步（持续）**：WebView + JS 三段式适配框架 + 适配包云端下发，先做 5-10 所种子学校（优先新版正方，JSON 接口最省事），之后开放社区投稿。
5. 合规红线：不代存学号密码（WebView 本地登录方案天然满足）；隐私政策补充课表数据说明。
